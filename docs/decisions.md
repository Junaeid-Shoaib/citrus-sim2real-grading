# Decisions

One line per decision: what, why, alternative rejected.

- Plain scripts in src/ instead of an installable package: simpler to run with `uv run python src/x.py`; rejected the uv --package layout as unneeded for a single project.
- uv for environment and packages: lockfile makes versions reproducible; rejected pip + requirements.txt.
- 256-bit phash over all 8 flips/rotations, Hamming threshold 24, connected components as duplicate groups: pairs at or under 24 looked like the same fruit on inspection; rejected 64-bit phash because it matched different oranges and chained about 2,000 images into one group.
- StratifiedGroupKFold with 20 folds (3 test, 3 val, 14 train) for the 70/15/15 split, stratified on source_class: balances each defect type across splits (grade balance follows) and keeps duplicate groups whole in one call; rejected a random stratified split because augmented copies would leak across splits.
- Balance defective by sampling 1,000 per defect folder before hashing: gives 3,000 per grade and halves hashing time; rejected keeping all 9,000 defective images because it would make defective 60% of the data.
- Train augmentation is horizontal + vertical flip and brightness/contrast/saturation jitter of 0.2, no hue jitter: top-down fruit has no "up", and hue is the cue separating green from fresh; rejected hue jitter because it could make an image contradict its label.
- Fixed label order GRADES = [defective, fresh, green] in dataset.py: every script imports the same mapping; rejected inferring order from the data because it can change with the CSV.
- Same-fruit leak documented, not fixed; real baseline treated as an upper bound: the phash check catches augmented copies but not the same physical orange photographed again. Evidence: for 120 sampled val images, the median distance to the nearest train image was 42 of 256 bits, about half had a train match at 40 or under, and visual pairs at 26 to 46 were clearly the same fruit (same stem, same spot pattern). Rejected re-grouping by ResNet feature similarity because oranges all look alike, so any threshold would also merge different fruit and be hard to verify. Possible later fix: evaluate on an independent orange dataset from different photographers.
- Phase B learning rate 1e-4 (run real_lrb1e-4) over 3e-4 (run real_lrb3e-4), picked on best val accuracy only: 0.9993 vs 0.9978. The gap is 2 of 1,350 val images, so it is not a meaningful difference; 1e-4 also trained more smoothly (3e-4 made train loss jump right after unfreezing). real_lrb1e-4 goes to Step 1.4.
- evaluate.py refuses to run if the run_id is already in experiments.csv: enforces scoring the test set once per experiment in code; rejected relying on discipline alone. The Grad-CAM code was checked on val images first so the single test run would not fail halfway.
- Grad-CAM written by hand (hook on layer4, gradient-weighted channels, ReLU, upsample) instead of the pytorch-grad-cam package: about 20 lines, no new dependency, and every line can be explained.
- Per-image test predictions saved to results/<run_id>_test_predictions.csv, so errors can be inspected without scoring the test set again. For real_lrb1e-4 the file was produced by a one-off pass that did not log to experiments.csv; the model was fixed and no decision depended on it, and it reproduced the logged 0.9985.
- Every synthetic orange gets a small dark stem or calyx at one pole, whatever its grade: in a 20-image sample of the real train split, stems, calyx and navels were visible on fresh and green fruit too, so if only defects were dark marks the model could learn "dark mark means defective". The stem colour is sampled per image from olive green (sRGB 0.30, 0.32, 0.12) to dark brown (0.20, 0.12, 0.05), the range seen on stems in a 32-image fresh and green train sample. The stem is a low raised dome about 4 to 8 px wide at 224 px, matching that sample, with noise mottling and bump so it reads as a scar, not a hole. Rejected: a fixed olive stem, because a light stem would not teach that dark marks at the pole are normal; no stem, because it is simpler but teaches a cue the real data contradicts. Based on train data only, not on test errors.
- EEVEE over Cycles for synthetic renders: headless benchmark on the M1 gave 0.34 s per frame for EEVEE vs 1.1 to 1.7 s for Cycles on Metal (plus a 112 s first kernel compile); the scene has one fruit and one light, so path tracing adds little. Cycles kept only as a fallback.
- All randomness lives outside Blender: generate.py turns a dict of parameters into an image and samples nothing, so the label is fixed before rendering and any image can be re-rendered from its row in labels.csv. Rejected sampling inside Blender because Blender's Python has no pyyaml and it would tie labels to render code.
- Standard view transform instead of Blender's default AgX: with Standard the sampled peel hue stays close to the hue in the output JPEG, which the real-vs-synthetic hue histograms rely on. Measured on the fruit pixels for sampled hue 0.075 and saturation 0.90: Standard gave median hue 0.067 and saturation 0.78; AgX gave 0.063 and 0.62.
- Peel pits from a Voronoi bump at 18 cells per unit, bump distance 0.02: at 60 cells per unit each pit was about 1 px at 224x224 and averaged away, and Blender 5.2's default bump distance of 0.001 made the pits about 1000x too shallow to see. Fine detail goes in the material, not the mesh, to keep memory low.
- Render metadata (date, time, frame, filename) turned off: Blender writes the render date into each JPEG by default, so reruns of the same parameters gave different files.
- Global shift of defective fruit also darkens (value x (1 - 2 x shift_brown)), with caps shift_brown <= 0.15 and shift_dull <= 0.2 asserted in generate.py. Darkening is needed because desaturating a bright orange alone rendered pastel peach, and brown is a dark orange. The caps are needed because at shift_brown 0.4 and shift_dull 0.3 a greenish base rendered beige, which would make "beige means defective" a shortcut and undo D5. At the caps, measured on fruit pixels, a hue 0.20 base renders at 65 degrees and saturation 0.50 (olive), and the worst case, hue 0.16, renders at 52 degrees and saturation 0.50. Rejected leaving the shift uncapped and relying on the sampler alone; the assert makes the limit hold in code.
- Rot modelled on 12 real rotten train images: most show one sunken olive-brown to dark-brown patch with a darker rim and no mould, and a few show heavy mould that is white at the margin and muted grey-green in the middle. So rot is a soft-edged patch with a sunken water-soaked rim, and mould grows out from the patch centre (the patch's radial falloff plus noise). Rejected mould from noise alone, which rendered as separate camouflage blobs, and multi-octave edge noise, which scalloped the edge at 224 px.
- Unused patch slots sit at the fruit's centre with radius 0.01, so every surface point is 1.0 from them and they can never show. A module-level assert checks the furthest reach (outer factor x radius + half the edge wobble) stays below 0.5, and used patches are asserted to have radius <= 0.7. Rejected relying on the 2.4 sampler alone.
- D5 revised: defective base hue comes from the matching real class per defect type (blackspot, canker, rotten), not from fresh plus green combined. The real train split has no deep-green defective fruit (grade-level hue 0.071 to 0.133, cankered up to 0.145), so deep-green defective renders would be a look the real data never shows; greenish-yellow canker keeps the D5 intent. Correction to an earlier summary: 0.079 to 0.141 was the material range under the first render calibration, not the real image range.
- Global shift changed from "browner" to "darker and slightly duller, same hue": real defective train fruit is 0.64 to 0.76x as bright as fresh, 0.89 to 0.97x as saturated, and not browner in hue. Caps shift_dark <= 0.65 and shift_dull <= 0.12 (small dulling, so a greenish base turns olive, not beige). Rejected the hue pull toward brown because the data contradicts it.
- Canker reworked from a few large grey lesions with yellow halos to many small raised corky brown marks on a yellow-olive base, reusing the masked Voronoi spot cells (distorted, corky colour, raised). 11 of 12 real cankered train images look like this and none had a bright halo. Rot patches are now the only use of the patch slots.
- Lighting: ambient world light 0.3 to 0.15, peel sheen (Specular IOR Level) 0.5 to 0.25, and light temperature centred on neutral 6500 K (narrow 6500, wide 4500 to 8500). At the old settings green and defective rendered 0.07 to 0.1 below the real saturation even at maximum material saturation; variant tests on 30 narrow renders showed the grey ambient and white sheen caused it. 5500 K also tinted the light backgrounds pink, while the real photos are white-balanced.
- Material colours calibrated by rendering, not by formula: rendered colour is not a simple function of material colour (lighting, sheen, clipping), so 30 narrow test images (6 per class) were rendered and the config adjusted until each class's rendered median sat inside the real 25th-75th percentile. Defective value is a pre-shift brightness calibrated per type, because rot's dark patch already darkens the fruit.
- Blackspot peel is wrinkled: a `wrinkle` parameter adds sunken creases from ridged noise through bump only (no extra geometry). Real blackspotted fruit is shrivelled, not smooth. Blackspot 0.4 to 1.0, canker 0 to 0.4, rot 0 to 0.3, fresh and green always 0.
- Canker marks cluster unevenly under a large-scale noise mask, with `canker_density` sampled per image (wide 0.3 to 1.0), because evenly spread Voronoi cells read as a regular polka-dot grid. The whole canker peel also gets a yellow-brown scabby mottle (sRGB 0.60, 0.50, 0.25) and rough bump; a grey-tan scab (0.55, 0.50, 0.36) cut rendered canker saturation to 0.70, the yellow-brown one gives 0.74 (real 0.78 to 0.87). Left as is, to be judged on the Step 2.4 histograms rather than tuned on 6 test renders.
- Wide green material hue moved from 0.14-0.20 to 0.145-0.205: at 0.14 the floor rendered at hue 0.133, below the real 5th percentile of 0.137.
- Dark green renders are kept as hard examples. Weak sampled light can make a green fruit darker than any real green and read brown-olive. Rejected a green-only brightness floor: lighting is sampled the same for every grade, so a class-specific floor would teach "dark means not green".
- Wide light colour temperature kept at 4500 to 8500 K. A brown-olive wide green was re-rendered at its sampled 5315 K and at 6500 K and the rendered hue did not change (0.133 both), so warm light was not the cause; narrowing the range was rejected.
- Mould powdered with fine noise but left inside the rot patch; listed in the spec's honest limits because real mould spreads with a soft fringe over up to half the fruit.
- Wide light strength narrowed from 200-800 W to 320-500 W (0.8 to 1.25x narrow); direction and colour unchanged. The Step 2.4 pilot showed many wide renders dimmer than any real photo, which look auto-exposed. Rejected normalising exposure on fruit pixels, because that would erase the real brightness difference between green and fresh fruit.
- Wide green material hue widened to 0.145-0.22: in the pilot, synthetic green had median hue 0.165 vs real 0.180 and under-filled the real peak near 0.20.
- Wide key light constrained to within 70 degrees of the camera direction (front to side lighting, never backlit): with light and camera directions drawn independently, many wide renders were backlit, and all grades rendered at about 0.7x the real brightness. The real photos are lit from the camera side. Rejected narrowing light strength alone, which a pilot showed did not help.
- Weak neutral-white fill light at the camera, wide only, fill_ratio 0.25 of the key's light on the fruit (power scaled by the squared distance ratio). White rather than more grey ambient, because grey ambient washed out saturation. Narrow keeps no fill so its colour calibration holds. Pilot 3: green value matched real (0.41 vs 0.42), fresh and defective rose by about 0.1.
- shift_dull cap lowered from 0.12 to 0.05: in pilot 3 the synthetic defective/fresh saturation ratio was 0.84 against real 0.89 to 0.97, while the value ratio (0.67) already matched real, so only the dulling was too strong.
- synthetic_report.py reports coverage: per grade and channel, the % of real train images whose median hue, saturation or value lies inside the synthetic 5th to 95th percentile. Matching medians alone does not show whether the synthetic set spans the real images. Go rule for the full batch: at least 80% on every grade and channel.
- Camera colour processing after rendering, wide only: per-image contrast then saturation boost (PIL ImageEnhance), sampled with the same ranges for every grade and stored in labels.csv. Real photos have phone-camera processed colour the renders could not reach (pilot 4 saturation coverage 28 to 75%). Done in Python after rendering, from render_path to path, so it is cheap to re-tune without re-rendering and is never applied twice. Rejected leaving it to Stage 3 colour jitter alone, because the real images really contain this colour and it belongs in the data. A one-sided boost (1.0 to 1.25 saturation) fixed defective (94%) but moved fresh and green up as a whole (78% and 44%), so the next version is two-sided.
- Camera saturation boost applied as an HSV S multiplier with V unchanged, and the boost made two-sided (saturation 0.85 to 1.2, contrast 0.95 to 1.15). ImageEnhance.Color blends toward grey, which also lowered brightness for orange fruit: with the two-sided range it cut defective value coverage from 84% to 75%. With the HSV version defective value coverage is 77.2%, the same as with no processing at all, which confirms saturation no longer touches brightness. Saturation coverage: 98% fresh, 100% green, 93% defective.
- Wide green material saturation widened downward to 0.82-1.0 so its spread before the boost matches real green; green saturation coverage went from 44% (one-sided boost) to 100%.
- Remaining colour gaps (defective value 77%, fresh darker overall, small narrow saturation misses) accepted and recorded in spec section 9 rather than tuned further, to stop fitting colour statistics on about 60 images per grade.
- Full batch rendered as 1,000 per grade per setting in chunks of 500 (one Blender process per chunk, resumable by skipping existing files): about 0.9 s per image, 51 min per setting. Spec section 9 now holds the full-batch coverage (wide defective value 84%, everything else 91-100%).
- phash duplicate check (D8b) kept for wide (26 groups of 2-3 images, mostly mixed grades) but not trusted for narrow, where identical framing and background chain 2,376 of 3,000 images into groups even though no two images match; noted as a limit instead of grouping narrow splits by phash, which would put almost all images in one split.
- Synthetic train/val split moved to src/split_synthetic.py, run after the images exist, so wide keeps phash duplicate groups in one split and both settings are stratified by grade and defect type. Alternative rejected: splitting in make_scene_params.py before rendering, which cannot see duplicates.
- Stated exception to the duplicate rule: narrow is split without phash groups, because its fixed framing chains 2,328 of 3,000 images into one group although no two match. Narrow still gets an 85/15 val split so both settings train the same way, but narrow val is for watching curves only, never for checkpoint selection.
- Review fixes before the v2 batch: oil-gland pits now use the per-image shifted coordinates like every other texture (they were identical across images); narrow renders are copied unchanged instead of going through an 8-bit HSV round trip and a second JPEG save; renders and processed images are written to a temporary name and renamed; make_scene_params.py refuses a folder that already has images; the report drops images with no fruit pixels instead of turning coverage into NaN.
- Camera framing at high fill and contrast pivoting on the whole image were documented as limits (spec section 9), not changed.
